# Cadence Playback Engine for Linux

This package runs the headless Playback Engine and its UPnP renderer. The existing `cadence-headless --dragonfish` daemon works on Linux beyond Dragonfish. The image supports `linux/amd64` and `linux/arm64`. Linux host networking is required for discovery and for a renderer to reach the advertised media address. The engine listens on TCP 4040 (TLS control) and 18890 (media); do not expose them to the internet. The host LAN IPv4 must be reachable from controllers and the renderer.

## Guided setup

For a first installation on an AMD64 or ARM64 Linux machine, download `install.sh` from the latest [Cadence GitHub release](https://github.com/matbhuvi-tech/Cadence/releases/latest), open a terminal in the downloaded file's folder, and run:

```sh
sh install.sh
```

The setup suggests the latest published release and the machine's LAN address. Press Enter to accept them, then enter the folder containing your music and a separate persistent data folder. It downloads the chosen release's Compose template and image, and starts the engine. Music is read-only. On Debian/Ubuntu, it installs missing Python, curl, Docker and Compose v2 packages from configured apt repositories, when those packages are available; an administrator password may be requested. On other distributions, install Docker Engine, the Compose v2 plugin, Python 3 and curl first. Docker must be running. The release image must exist and its GHCR package must be public or accessible to the machine.

For TrueNAS SCALE 25.10 or later, first configure the Apps pool in TrueNAS, then download `install.sh` to the NAS and run `sudo sh install.sh` in the TrueNAS shell. Provide existing music and persistent data paths under `/mnt`; the parent of a new data folder must already exist. The setup creates a custom app through TrueNAS middleware so it appears under **Apps**. It does not install packages into TrueNAS. Grant UID/GID 568 read access to music and write access to an existing data folder using dataset ACLs; a new data folder is assigned to that identity. Use the Apps screen for status and logs. TrueNAS 24.10/25.04 users can use the manual YAML method below; the automated API path has not been verified on those versions.

This is a first-install wizard: it refuses to replace an existing setup. If setup stops after writing its configuration, inspect the displayed error and the `cadence-installation` directory on TrueNAS or `~/cadence-playback-engine` on Linux. The configuration files may be moved aside before retrying **only after checking that no engine is running**; keep the persistent data directory. For existing installations, use the upgrade and rollback instructions below. The suggested IP is based on the default network route, so check it on machines with more than one network. The generated pairing token remains private in the data directory.

## Docker Compose

1. Install Docker Engine and Compose on Linux. Obtain a published release tag from the repository releases and ensure the GHCR package is public or authenticate to GHCR. A release publication creates `ghcr.io/matbhuvi-tech/cadence-playback-engine:<release-tag>`; the image does not exist until a release is published. `latest` follows stable releases only. Pin a tag or immutable digest for predictable upgrades.
2. Copy `compose.yml` and `.env.example` into a directory. Copy `.env.example` to `.env` and set `CADENCE_IMAGE`, `CADENCE_ADVERTISED_IP`, `CADENCE_HOST_DATA_DIR`, and `CADENCE_HOST_MUSIC_DIR` to your actual image, LAN IPv4, and **existing absolute** host directories. The data directory must be writable by UID/GID 568; the music directory must be readable and searchable by that user. Configure ACLs on NAS datasets rather than changing ownership of a shared music library.
3. Run `docker compose config` to review the configuration, then `docker compose pull` and `docker compose up -d`. Check `docker compose ps` and `docker compose logs playback-engine`. Startup may fail if the address, permissions, memory limit, lock limit or ports are unsuitable. Pair with the controller using the engine address and the secret in the data directory (`pairing-token`); protect it as a password.

The recipe mounts music read-only, stores state outside the container, drops other capabilities, supplies `IPC_LOCK` and an unlimited memlock limit, and places a 4 GiB cgroup memory limit on the service. Increase the memory limit for larger tracks and account for host memory and ZFS ARC; locked memory is not a pageable fallback. The image health check is a local HTTPS readiness probe every 60 seconds. For optional tag writes, explicitly change both the music bind to writable and `CADENCE_MUSIC_READ_ONLY` to `false`, and ensure appropriate ACLs. Only enable this where writes are intended.

Multiple mounted library roots can be listed in `CADENCE_BROWSE_ROOTS` separated by `:`. Each must be an actual mounted directory, distinct from application data. The default paths, ports, and optional `CADENCE_HEADROOM_MB`, `CADENCE_MIN_LOCKABLE_MB`, and `CADENCE_PINNED_RS130_UDN` use the existing daemon interface. `CADENCE_ALLOW_LOOPBACK` is for tests only. Keep the music path stable across upgrades so catalog paths continue to resolve.

## TrueNAS SCALE 24.10 and later

Modern SCALE apps use Docker Compose. Prepare separate persistent datasets for engine data and music, with the ACLs above. In **Apps > Discover Apps > more menu > Install via YAML**, paste the contents of `compose.yml` into Custom Config. Replace *all* `${...}` expressions with literal values, including an actual published image tag, the TrueNAS LAN IPv4 and absolute dataset paths (quote paths containing spaces). Do not rely on a local `.env` file in the UI. Save and inspect the app logs. The image's UID/GID is 568; verify dataset ACLs rather than assuming a particular TrueNAS ACL preset. Host networking and IPC_LOCK must be accepted by the host. See [TrueNAS custom app instructions](https://apps.truenas.com/managing-apps/installing-custom-apps/). Dragonfish 24.04 uses a different Kubernetes app system; its legacy recipe is in `deploy/truenas-dragonfish/`.

## Native Linux systemd

Build `cadence-headless` for the host architecture with `cargo build --locked --release --manifest-path src-tauri/Cargo.toml --no-default-features --features bundled-sqlite --bin cadence-headless` on a Linux build host. Install the resulting binary as `/usr/local/bin/cadence-headless`, create a non-root UID/GID 568, `/var/lib/cadence` writable by that identity, and a readable `/music` mount. Copy `playback-engine.env.example` to `/etc/cadence/playback-engine.env`, set the LAN address and paths, and install `cadence-playback-engine.service` to `/etc/systemd/system/`. Adjust `ReadWritePaths`, identity and `MemoryMax` to match the host; music and data must be separate directories. Then run `systemctl daemon-reload`, `systemctl enable --now cadence-playback-engine` and inspect `journalctl -u cadence-playback-engine`. The binary, service and env file must be installed by an administrator. This example assumes systemd, cgroup v2 and permissions to grant CAP_IPC_LOCK.

## Persistence, upgrades and rollback

The data directory contains the SQLite database and WAL, engine identity, TLS keys/certificate, pairing token and backups. Preserve the **entire** directory, restrict access and back it up separately from the music library. The built-in versioned backup includes a consistent SQLite snapshot and identity/TLS files, but **does not include `pairing-token`**; back up that secret separately or preserve the entire stopped data directory. If using `CADENCE_PAIRING_TOKEN`, preserve that external secret as well. Backups include private keys and must be protected. Back up music separately.

Before upgrading, stop playback and the service (`docker compose stop`), wait for it to exit, then run the old image's offline backup using `docker compose run --rm --no-deps playback-engine --backup pre-upgrade-YYYYMMDD`. Use a unique tag: reusing one replaces that backup. Make an independent copy or storage snapshot of the complete stopped data directory, including `pairing-token`, outside the data directory. Record the old image tag/digest. Change `CADENCE_IMAGE` to the new published version, pull it and run `docker compose up -d`; check logs, readiness, pairing and playback. Do not run backup or restore concurrently with the daemon.

To roll back, stop the service. Restore the complete pre-upgrade data-directory snapshot (including the pairing token) while it is stopped, or use the matching old image and `docker compose run --rm --no-deps playback-engine --restore pre-upgrade-YYYYMMDD`, restoring the separately saved token if needed. Set `CADENCE_IMAGE` back to the matching old version and start the service. The built-in restore overwrites database and identity files and removes SQLite WAL/SHM; keep an independent copy of the current data before restoring. A database upgraded by a newer version is not assumed compatible with an older binary. Test recovery on a separate copy before relying on a backup. For systemd use `systemctl stop`, then invoke the same binary as UID 568 with `--app-data-dir /var/lib/cadence --backup <tag>` or `--restore <tag>` while stopped.

## Publishing

Publishing a GitHub release triggers `.github/workflows/playback-engine-image.yml`: Buildx builds both architectures and pushes a manifest to GHCR using `GITHUB_TOKEN` with `packages: write`, then attaches `install.sh` and `install.py` to the release using `contents: write`. Published tags include the release tag and commit SHA; stable releases also update `latest`. A manual workflow dispatch builds without pushing. GitHub package visibility and repository/package permissions must be configured by the repository owner; the workflow does not make a package public automatically. See [GitHub's image publishing guidance](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images).
